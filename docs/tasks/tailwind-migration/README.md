## 1. 已确认的目标与边界

- 覆盖整个 `apps/web`：所有页面、布局、公共组件以及路由中的固定内联样式。
- 保持现有视觉效果、响应式布局、无障碍能力和业务交互；不修改 API、数据流、路由、权限或持久化契约。
- 保留当前 Tailwind CSS v4、Vite 集成和 DaisyUI。保留插件不等于将现有公共组件改成 DaisyUI 默认设计。
- 最终自有源码只有 `apps/web/src/index.css` 一个 CSS 文件，由 `src/main.tsx` 唯一引入。
- 入口允许导入 Tailwind、DaisyUI 插件配置和必要第三方样式，并声明主题变量、主题动画及全局基础规则。
- 页面和组件样式直接写在组件的 Tailwind 类名中；禁止通过 `@apply`、新增组件选择器、CSS-in-JS 或组件内 `<style>` 转移旧规则。
- 所有固定值 `style` 改成工具类；运行时计算的地图坐标、路线进度等数值可以通过 `style` 或 CSS 变量传递。第三方库自身生成的样式不受此限制。
- 第三方依赖源码、独立 SVG 素材内部样式以及构建生成的 CSS 不计入“单一自有 CSS 文件”；不编辑依赖和生成文件来满足检查。

### 视觉和层叠规则

1. 以迁移前浏览器的实际计算样式为准，保留尺寸、颜色、字重、间距、阴影和断点。无法精确对应标准工具类时，使用 Tailwind 任意值。
2. 部分业务 CSS 使用未定义的变量，或者带有不同于公共主题的 fallback。先记录实际生效值，不顺带补齐变量或统一颜色，避免引入视觉改版。
3. 保留原 CSS 的断点边界。只有数值完全等价时使用 `sm:`、`md:`、`lg:`，否则使用任意断点；不得将 `639px`、`39.99rem`、`47.99rem` 等无条件四舍五入。
4. 工具类必须是源码可扫描的完整字符串。按钮变体、徽标 tone、时间线状态使用穷举映射，不写 `bg-${color}` 一类运行时拼接。
5. 同一属性的基础类和变体类尽量互斥。原调用方确需覆盖公共组件默认值时，在调用方使用局部 important 工具类；不要依赖 `className` 中字符串的先后顺序。
6. 原生元素优先直接添加类；不可直接控制的第三方 DOM、现有组件内部节点可在组件中使用 Tailwind 任意后代变体。不得继续依赖已删除的自定义类名。
7. 公共组件移除旧类名时，必须同步处理业务 CSS 对这些类名的引用；详见步骤 01，避免后续模块还没迁移就失去样式。

## 4. 每一步的验证与提交流程

所有命令从仓库根目录运行。前端使用自身的 pnpm 配置，不假设根目录存在 `package.json`。

1. 阅读本文件和对应子计划，检查 `git status --short`，确认前一步已提交，识别用户原有修改。
2. 只实现当前子计划及其明确列出的兼容性调整，同时修改依赖旧 CSS 路径或类名的现有测试。
3. 运行子计划列出的定向测试，再执行共同门禁：

   ```powershell
   pnpm --dir apps/web lint
   pnpm --dir apps/web build
   git diff --check
   ```

4. 根据步骤 00 的同一组基线、数据和视口进行浏览器视觉及键盘检查。JSDOM 测试通过不能证明 CSS 视觉等价。
5. 在当前子计划“执行记录”填写实际结果，并同步本文件状态。验证失败或环境不足时记录阻塞原因，不创建“已完成”提交，不跳到下一步。
6. 显式暂存本步骤文件及其计划记录，不使用 `git add .` 或 `git add -A` 混入用户修改。检查 `git diff --cached --stat` 和 `git diff --cached`。
7. 使用该子计划提供的完整标题和正文提交，运行 `git log -1 --format=full` 与 `git status --short` 核对结果，再开始下一步。只做本地 commit，不自动 push、合并或发布。

每个子计划一个提交；测试和进度记录包含在同一提交中，不另拆成空提交。发现验证失败时先修复当前步骤。已完成提交需要回退时，使用针对该提交的 `git revert`，不使用破坏性的 reset 清除其他人的工作。

### Commit message 规则

遵循 [仓库提交规范](../../commit-conventions.md)：`<emoji> <type>(<scope>): <description>`。本次用户进一步要求**每个 commit 都必须有正文**，即使仓库一般规则允许小提交省略正文。

- 标题使用对应 Emoji、英文小写开头的祈使描述，无句号，建议不超过 72 字符。
- 标题后空一行，正文说明迁移原因、主要修改和影响；可附真实验证结果，不写未执行的检查。
- 本次属于保持外部行为的样式实现重构，实施提交使用 `♻️ refactor(web): ...`；计划文档使用 `📝 docs(web): ...`。
- 多行正文可以写入仓库外临时文件后使用 `git commit --file <文件路径>`，或使用独立的标题／正文参数；必须保留真实换行。
- 仓库当前存在用户原有未跟踪文件 `docs/commit-conventions.md`。本轮仅读取其规则，不替用户修改或暂存；后续执行前重新检查状态。
